# Design

## Context

See proposal.md for motivation. The relevant parts of the current system:

- Data model `exercises` -> `workout_exercises` (ordered by `position`) -> `sets` (`server/db/schema.ts`). Editing a workout replaces all its exercises and sets in one transaction (`replaceWorkout` in `server/services/workouts.ts`).
- Validation is a shared, framework-free function (`validateWorkout` in `shared/workouts.ts`) used by both the form and the server.
- `getLastTime` and `getExerciseProgress` query every workout; neither knows about drafts.
- The API request guard (`server/lib/request-guard.ts`) accepts only JSON bodies of at most 256 KB; the CSP allows scripts and connections only from `'self'` and blocks frames.
- The trainer's PDF is a Google Sheets export. Its text extraction interleaves columns (`2010` and `2` come out as `20102`), and the YouTube links exist only as link annotations whose rectangles overlap the name cells, not as text.

## Goals / Non-Goals

**Goals:**
- Drafts reuse the existing workout tables and screens instead of adding a separate plan model.
- The PDF parser is a pure function over extracted text positions and link rectangles, so it is unit-tested without a browser.
- No weakening of the request guard or CSP.
- Gym mode survives page reloads and short connection drops without losing ticked sets.

**Non-Goals:**
- Offline mode or a service worker; a lost connection only delays saving while the page stays open.
- Generic PDF or spreadsheet import; only the trainer's table layout.
- Muscle groups. The swap list only has to accept an extra filter later (see D7).

## Decisions

### D1. Status on `workouts`, completion flag on `sets`
New migration:
```
workouts.status    text not null default 'done'   -- 'draft' | 'done'
sets.completed     integer not null default 1     -- boolean
exercises.video_url text null
```
Existing rows get `done` / completed, so history and progress are unchanged. Drafts are created with sets `completed = 0`. An index on `workouts(status, date)` supports the home screen and the filtered queries.
- Alternative: separate `plans` / `plan_items` tables copied into a workout on start. Rejected: the user overwrites planned values and does not want planned-vs-actual, so a second model would duplicate every screen and validation rule for nothing.

### D2. Read the PDF in the browser with `pdfjs-dist`
The import page loads `pdfjs-dist` lazily, extracts text items (string plus x/y) and link annotations (URL plus rectangle) from page 1, and passes them to the parser. Only structured JSON reaches the server.
- The worker is bundled as a same-origin asset and set as `workerSrc`. pdf.js 6 no longer evaluates generated code (the `isEvalSupported` option was removed), so it runs under the existing `script-src 'self'` CSP.
- Alternatives: server-side parsing (`unpdf`) would require multipart or large bodies and loosening the recently hardened request guard; a Python helper adds a runtime to the Docker image. Both were rejected.

### D3. Parser by column positions, not text order
All code, database columns, API fields, file names and test names are in English. Polish appears only as data: exercise names as the user enters or imports them, and the PDF's header labels, which live in a single constant that maps each label to an English field (`Nr` -> `number`, `Nazwa Ćwiczenia` -> `name`, `Serie` -> `sets`, `Ruchy` -> `reps`, `Tempo` -> `tempo`, `RIR` -> `rir`, `Ciężar` -> `weight`). Nothing past that mapping uses the Polish labels.

`shared/plan-import.ts` exposes `parsePlan({ items, links }) -> { rows, errors }`, where each row is `{ name, sets, reps, durationS, weightKg, videoUrl }`:
1. Find the header row by its labels (`Nr`, `Nazwa Ćwiczenia`, `Serie`, `Ruchy`, `Tempo`, `RIR`, `Ciężar...`). Missing labels mean "not a plan" (spec: Supported plan format).
2. Derive column boundaries from header x positions, then group the items below the header into rows by y (with tolerance) and assign each item to a column by x. This avoids the `20102` interleaving.
3. Parse cells: Serie as an integer; Ruchy as reps, or as seconds with an `s` suffix; Ciężar as a decimal with a comma or point and a `kg` suffix, where `a/b` takes `a`. Weight is ignored for timed rows. Tempo and RIR are never read.
4. Assign each link to the row whose name cell its rectangle overlaps vertically; keep only `https:` links.
The tests use a synthetic plan PDF generated by `scripts/make-plan-fixture-pdf.mjs`: same layout as the trainer's export, but made-up exercises, values and `example.com` links, so no real training data or video links are stored in the repository. Its extracted items and links are committed for unit tests; the PDF itself is used by the E2E test.

### D4. Matching on the client, saving in one server transaction
- `importNameKey(name)` = `exerciseNameKey(name)` with trailing punctuation and an `'s` / `’s` suffix removed. Lives in `shared/` and is used for review matching against `GET /api/exercises`.
- `POST /api/plan-imports` receives the confirmed review: `date`, `sessionType`, and rows with either `exerciseId` or `newExercise { name, kind }`, plus `videoUrl` and `sets`. One transaction creates the new exercises (normal name rules apply), fills `video_url` only where it is null, and creates the draft. A failure creates nothing.
- Alternative: the client calls the existing exercise and workout endpoints one by one. Rejected because a failure mid-way would leave orphan exercises.

### D5. Workout API shape
- `POST /api/workouts` accepts an optional `status` (`draft` | `done`, default `done`); each set accepts an optional `completed` boolean.
- `PUT /api/workouts/:id` keeps the stored status; it cannot change it. Clients send `expectedStatus` (gym mode and the draft editor send `draft`); a mismatch returns 409, so a save that arrives after finishing cannot rewrite the done workout with its unticked planned sets. Gym mode also locks its inputs while finishing.
- `POST /api/workouts/:id/finish` (draft only) drops uncompleted sets and empty exercises, validates the result as done, and sets the status in one transaction.
- `GET /api/workouts` returns `status` per item; the home page splits drafts (date ascending) from done workouts (newest first).
- `validateWorkout(input, kindOf, { mode })`: `draft` skips the required-value check; everything else is shared.

### D6. Gym mode saving through debounced whole-draft PUTs
Gym mode keeps the draft in page state. Every change schedules a save (about 400 ms debounce) of the whole draft via the existing `PUT`. At most one request runs at a time; a change made during a request sends the latest state afterwards. On failure the status shows "Not saved" and the save retries with backoff; leaving the page while unsaved shows a browser confirmation.
- Alternative: per-set PATCH endpoints. Rejected: set ids change on every replace, a draft is a few KB, and a single-user app has no concurrent writers.

### D7. Swap list from the exercise list with last-done date
`GET /api/exercises` adds `lastDoneOn` (latest date among done workouts, or null) and `videoUrl` per exercise. The swap dialog sorts and searches on the client and excludes exercises already in the draft. The muscles change can later add a filter or ranking on the same list without changing the swap flow. Sets for a swapped exercise follow the spec (same kind keeps sets; otherwise last-time values from `GET /api/exercises/:id/last?before=<draft date>`).

### D8. Drafts excluded from history, last-time and progress
`getLastTime` and `getExerciseProgress` add `status = 'done'`. The home history list filters on the client from the status in D5.

### D9. Video links
Zod schema: `https:` URL, at most 2048 characters, empty string treated as null. Rendered as a link with `target="_blank" rel="noopener noreferrer"`; no embedding, so `frame-src` stays blocked.

### D10. Defaults set by the import review
The draft date defaults to tomorrow in local time (same `toIsoDate` helper as the form) and the session type to trainer; both are editable in the review.

## Risks / Trade-offs

- [The trainer changes the sheet layout (extra or merged columns)] → The parser locates columns by header labels rather than fixed positions; anything it cannot map produces "could not read as a plan" instead of wrong data. A CSV import can be added later if this recurs.
- [pdf.js falls back to a blob worker that the CSP blocks] → Explicit same-origin `workerSrc`; the E2E test runs the import under the production CSP.
- [pdf.js size, about 1 MB] → Loaded only on the import page through a dynamic import.
- [Whole-draft PUT could overwrite a newer save if responses arrive out of order] → Saves are serialized (D6), so only one request is in flight.
- [Name matching misses a variant spelling and creates a near-duplicate] → Every unmatched row needs explicit confirmation in the review and can be linked to an existing exercise instead.
- [Ticked sets lost if the browser is closed while offline] → Accepted (no offline mode); the unsaved indicator and leave-page confirmation make the state visible.

## Migration Plan

1. Generate migration `0001` with drizzle-kit (three columns plus index, defaults as in D1). It is applied automatically on startup, like `0000`.
2. Deploy as usual. Existing data needs no backfill beyond the column defaults.
3. Rollback: the columns are additive and the previous version ignores them, but drafts would then appear as normal workouts. Delete drafts before rolling back, or restore the database file from backup.
